# コーディングルール

## 構成と読みやすさ

- Flask・Peewee・SQLiteと、`docs/ai_context.md` に記載した採用パッケージを使う。独自の認証・CSRF処理を増やす前に採用パッケージへ合わせる。
- 初学者が役割を理解できるファイル名・関数名を使い、処理を小さく分ける。コメントには必要な理由を日本語で書く。
- `app.py` は起動とURLごとの処理、`config.py` は設定、`database.py` はDB接続、`models.py` はテーブル、`forms.py` はフォームと入力検証を担当する。必要な段階で作成・分割する。
- HTMLは `templates/`、CSS・JSは `static/`、ユーザー投稿画像は直下の `uploads/` に置く。複雑なフロントエンド構成や外部CDNは追加しない。

## 認証・入力・秘密情報

- ログイン操作はFlask-Loginで扱い、セッションはFlask-SessionとCacheLibで `instance/sessions/` に保存する。ログインから24時間の期限をサーバー側でも確認する。
- フォームはFlask-WTFを使い、すべてのPOSTをCSRF保護する。非同期のいいね送信にもトークンを渡す。
- 必須入力、文字数、メール形式、画像内容はサーバー側で検証する。メール形式はemail-validatorを使い、今回メール送信や到達確認は行わない。
- パスワードはWerkzeugでハッシュ化し、平文で保存しない。ログイン・ログアウト時は古い認証状態を残さない。
- 秘密鍵は環境変数 `PHOTO_SHARE_SECRET_KEY` から読む。開発時はpython-dotenvで `.env` を読み込み、秘密の値をコード・設計資料・ログに書かない。
- 認証用CookieにはHttpOnlyとSameSiteを設定する。ローカルのHTTPと、将来のHTTPS環境の設定を混同しない。
- ログイン状態だけでなく、投稿・コメントの所有者もサーバー側で確認する。画面のボタンを隠すだけで制限したことにしない。
- Jinjaの自動エスケープを保ち、利用者が入力した名前・投稿文・コメントに `safe` を使わない。
- デモログインは有効設定かつローカル接続の場合だけ許可し、固定のサンプル利用者を使う。送信されたIDで利用者を選ばず、既存のログインを勝手に切り替えない。

## DBと画像

- Peeweeで一意制約と外部キーを設定し、SQLiteの外部キー制約を有効にする。起動時に既存データを初期化しない。
- DB接続はリクエスト開始時に開き、終了時に閉じる。日時はUTCで保存し、日本時間で表示する。
- 写真はPillowで画像内容・形式・容量を検証し、向き補正と位置情報などのメタデータ除去を行う。
- 写真の保存名はUUIDで生成し、元のファイル名を保存パスに使わない。配信は投稿に登録された画像に限定する。
- 投稿削除では関連するいいね・コメントと写真を削除する。途中で失敗した場合に、DBと写真の食い違いを残さないようにする。

## 画面・検証・Git

- 画面表示はGET、変更はPOST。成功後はリダイレクトし、再読み込みによる重複投稿を防ぐ。エラーと戻り先は設計資料に従う。
- 通常の入力エラーは元のフォームに理由を表示し、可能な範囲で文章を保持する。パスワードを再表示しない。
- アニメーションに頼らず操作できる状態を保ち、ライト・ダーク、PC・スマホ、動きを減らす設定を確認する。
- 意味のある成功・失敗・所有者制御の確認をunittestで行う。低影響の文書変更のために実装をなぞるテストを増やさない。標準の確認コマンドは `.venv/bin/python -m unittest discover -s tests -v`。
- 実ブラウザの確認と自動テストを区別し、検証していない機能を完了扱いにしない。確認結果は `docs/tasks.md` に記録する。
- `.venv/`、`.env`、DB、セッション、投稿画像、秘密鍵をGitへ追加しない。`requirements.txt` と秘密の値を含まない `.env.example` は管理する。
- 既存の変更と利用者データを保護する。コミット・push・公開は本人が依頼した範囲で行う。
- 仕様変更時は `docs/requirements.md` と関係する画面・URL・DB・コンテキストを合わせて更新する。
